# Quark Facades — Система фасадов фреймворка

[![License](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Фасады — это центральный архитектурный механизм фреймворка Quark.
Они предоставляют единую точку доступа ко всем сервисам приложения
через объект `$APP` и реализуют паттерн **Service Locator** с ленивой загрузкой.

---

## Что такое фасад и зачем он нужен

**Фасад** (Facade) — это паттерн проектирования, который предоставляет
упрощённый интерфейс к сложной подсистеме. Вместо того чтобы напрямую
создавать объекты и управлять их зависимостями, вы обращаетесь к ним
через единый объект-посредник.

В Quark фасады решают несколько задач:

- **Единая точка доступа** — все сервисы доступны через `$APP`
- **Ленивая загрузка** — сервис создаётся только при первом обращении
- **Автоматическая конфигурация** — каждый фасад читает свой `.ini` файл
- **Слабая связанность** — контроллеры не знают, как устроены сервисы внутри

Без фасадов код контроллера выглядел бы так:

```php
// Без фасадов — вручную создаём все зависимости
$pdo = new PDO('sqlite:database.db');
$orm = new QORM($pdo);
$presenter = new Presenter(['templates' => ['folder' => 'app/views/']]);
$presenter->file('page.html')->display(['title' => 'Hello']);
```

С фасадами:

```php
// С фасадами — всё уже готово
$APP->template->file('page.html')->display(['title' => 'Hello']);
```

## Текучий интерфейс (Fluent Interface)

Многие фасады реализуют **текучий интерфейс** — стиль программирования,
при котором методы возвращают `$this`, позволяя выстраивать цепочки вызовов.

```php
// Цепочка вызовов — каждый метод возвращает объект
$APP->template
    ->themelink('/assets/')
    ->file('admin/dashboard.html')
    ->display($content);

// Эквивалентно:
$tpl = $APP->template;
$tpl->themelink('/assets/');
$tpl->file('admin/dashboard.html');
$tpl->display($content);
```

Текучий интерфейс делает код более читаемым и выразительным,
особенно при работе с ORM:

```php
$users = $APP->db
    ->connect('main')
    ->table('users')
    ->where(['status' => 'active'])
    ->orderBy('name ASC')
    ->limit(10)
    ->select();
```

**Преимущества текучего интерфейса:**
- Код читается как предложение на естественном языке
- Меньше промежуточных переменных
- Легко добавлять/убирать шаги в цепочке

**Ограничения:**
- Сложнее отлаживать — ошибка в цепочке не всегда указывает на конкретный метод
- Не все операции логично выражаются цепочкой

## Как работает механизм фасадов

### Ядро: класс APP

Всё начинается с класса `APP` в `engine/core/core.php`.
Он расширяет `stdClass` и перехватывает обращения к несуществующим свойствам
через магический метод `__get()`:

```php
class APP extends stdClass
{
    public function __get($unit)
    {
        // Ищем файл фасада в директориях
        foreach ($this->core_config['path_units'] as $modelDir)
        {
            $filename = $modelDir . DIRECTORY_SEPARATOR . "$unit.php";
            if (is_readable($filename))
            {
                // Загружаем фасад и сохраняем результат
                $this->$unit = include($filename);
            }
        }
        return $this->$unit;
    }
}
```

Когда вы пишете `$APP->template`:
1. PHP не находит свойство `template` в объекте
2. Вызывается `__get('template')`
3. Ищется файл `engine/facades/template.php`
4. Файл подключается через `include`
5. Результат (`return new Presenter(...)`) сохраняется в `$APP->template`
6. При следующем обращении `__get` уже не вызывается — свойство существует

### Ленивая загрузка

Фасады загружаются **только при первом обращении**. Если в запросе не используется
`$APP->cache` — Memcached не инициализируется. Это экономит ресурсы.

```php
// Фасад 'db' загрузится только здесь, при первом обращении
$users = $APP->db->connect('main')->table('users')->select();

// Повторное обращение — уже загруженный объект, без include
$count = $APP->db->connect('main')->table('users')->count();
```

### Доступ к другим фасадам внутри фасада

Внутри файла фасада переменная `$this` указывает на объект `$APP`.
Это позволяет фасадам зависеть друг от друга:

```php
// engine/facades/controller.php
return new Controller(
    $this->config->get(),   // $APP->config
    ['files' => $this->utils->files] // $APP->utils
);

// engine/facades/user.php
return new CMSUser($this->dba, $this->config); // $APP->dba, $APP->config

// engine/facades/catalog.php
return new SimpleCatalog($this->db, $this->config); // $APP->db, $APP->config
```

## Структура файла фасада

Каждый фасад — это PHP-файл в директории `engine/facades/`.
Файл должен вернуть объект через `return`. Стандартная структура:

```php
<?php
namespace App\Facade;

# ---------------------------------------------------------------- #
#                  ОПИСАНИЕ ИНТЕРФЕЙСА (опционально)               #
# ---------------------------------------------------------------- #
interface QMyServiceInterface
{
    public function doSomething();
}

# ---------------------------------------------------------------- #
#                 РЕАЛИЗАЦИЯ ИНТЕРФЕЙСА                            #
# ---------------------------------------------------------------- #
class MyService implements QMyServiceInterface
{
    public $config;

    public function __construct($config = [])
    {
        $this->config = $config;
    }

    public function doSomething()
    {
        // ...
        return $this; // для текучего интерфейса
    }
}

# ---------------------------------------------------------------- #
# --------------[ СОЗДАЕМ И ПОДКЛЮЧАЕМ ИНТЕРФЕЙС ]---------------- #
# ---------------------------------------------------------------- #

return new MyService( $this->config->get(__file__) );
```

Файл конфигурации `engine/facades/myservice.ini` создаётся рядом:

```ini
[settings]
option1 = "value"
option2 = 42
```

## Конфигурация фасадов

### Автоматическое чтение конфига

Фасад `config` (`engine/facades/config.php`) предоставляет метод `get()`,
который автоматически находит `.ini` файл рядом с вызывающим PHP-файлом:

```php
// Внутри engine/facades/template.php:
$this->config->get()

//Вы можете добавить немного бюрократии и вписать __file__:
$this->config->get(__file__)

// Далее метод читает: engine/facades/template.ini
```

Это не влияет на результат выдачи, но второй способ сработает быстрее (с использованием __file__), из-за того, что это избавляет фреймворк от необходимости трассировать цепочку вызова и он может сразу перейти к чтению конфигурации. Механизм $APP->config->get() работает и для контроллеров, служб, провайдеров данных, поэтому ядру нужно некоторое процессорное время, что бы сориентироваться, кто именно вызывает конфигурацию, что бы не обременять разработка построением путей и парсингом ini файла.


Это соглашение позволяет каждому фасаду иметь собственный конфиг
без явного указания пути.

### Пример: конфигурация шаблонизатора

`engine/facades/template.ini`:
```ini
[compilation]
caсhe = false
folder = "%TEMP%/templater/"

[templates]
folder = app/views/
```

`engine/facades/template.php`:
```php
return new Presenter( $this->config->get(__file__) );
```

### Переменные окружения (.env)

Глобальная конфигурация фреймворка хранится в `.env`:

```ini
[core]
path = "engine/core/"

[vendor]
path = "engine/vendor"

[facades]
path   = "engine/facades"
models = "app/models"
```

Секция `[facades]` определяет директории, в которых ищутся фасады.
Можно добавить несколько директорий — фреймворк будет искать фасад в каждой из них.

## Создание собственного фасада

> [!WARNING]
> Внимание: Разработку не следует создавать собственные фасады. Если вы хотите добавить свой фасад для вызова, используйте модель (app/model). Quark фундаментально ориентирован на MVC, используйте модели! 


> [!CAUTION]
> Создание собственных фасадов не гарантирует их работоспособность при миграции версий. Используйте директорию app/model/. 
> Поведение будет идентичным, но отделит код фреймворка от кода приложения




Чтобы добавить новый сервис в приложение, достаточно создать файл в директории фасадов.

### Шаг 1: Создать файл фасада

`engine/facades/mailer.php`:

```php
<?php
namespace App\Facade;

class Mailer
{
    private $config;

    public function __construct($config = [])
    {
        $this->config = $config;
    }

    public function to($address)
    {
        $this->config['to'] = $address;
        return $this; // текучий интерфейс
    }

    public function subject($subject)
    {
        $this->config['subject'] = $subject;
        return $this;
    }

    public function send($body)
    {
        return mail(
            $this->config['to'],
            $this->config['subject'],
            $body,
            "From: {$this->config['from']}"
        );
    }
}

return new Mailer( $this->config->get(__file__) );
```

### Шаг 2: Создать конфиг (опционально)

`engine/facades/mailer.ini`:

```ini
from = "noreply@example.com"
```

### Шаг 3: Использовать в контроллере

```php
// app/controllers/contact.php
$APP->mailer
    ->to('admin@example.com')
    ->subject('Новое сообщение')
    ->send($content['message']);
```

Никакой регистрации, никаких дополнительных настроек — фасад готов к работе.


> [!TIP]
> Вы можете переопределить и расширить возможности фасада фреймворка, создав одноименный файл в директории app/model. 
> Если вы решите так поступить, позаботьтесь об обратной совместимости предлагаемого решения с другими компонентами системы.

## Добавление директории фасадов

Если нужно разместить фасады в нескольких директориях (например, отделить
фасады приложения от фасадов ядра), добавьте путь в `.env`:

```ini
[facades]
path   = "engine/facades"
models = "app/models"
```

Фреймворк будет искать фасад последовательно в каждой директории.
Если фасад найден в первой — поиск прекращается.

## Типовые примеры использования

### Работа с базой данных

```php
// Подключение к именованной БД из db.ini
$users = $APP->db->connect('main')->table('users')->select();

// С условиями
$active = $APP->db
    ->connect('main')
    ->table('users')
    ->where(['status' => 'active'])
    ->orderBy('name ASC')
    ->limit(10)
    ->select();
```

### Рендеринг шаблона

```php
// Простой вывод
$APP->template->file('page.html')->display(['title' => 'Главная']);

// С базовым URL для ресурсов
$APP->template
    ->themelink('/assets/')
    ->file('admin/dashboard.html')
    ->display($content);
```

### Работа с URL

```php
$host = $APP->url->host();   // example.com
$home = $APP->url->home();   // /myapp/
$page = $APP->url->page();   // catalog/phones
$uri  = $APP->url->uri();    // /myapp/catalog/phones?sort=price
```

### Логирование

```php
$APP->log->info('Пользователь вошёл', ['login' => $login]);
$APP->log->error('Ошибка подключения к БД', ['host' => $host]);
$APP->log->debug('Запрос выполнен', ['sql' => $query]);
```

### Кеширование

```php
// Получить из кеша или вычислить
$data = $APP->cache->get('catalog_list');
if (!$data) {
    $data = $APP->db->connect('main')->table('catalog')->select();
    $APP->cache->set('catalog_list', $data, 3600); // 1 час
}

// Инвалидация
$APP->cache->delete('catalog_list');
```

### Определение устройства пользователя

```php
$ua = $APP->useragent;
$ua->parseUserAgentString($_SERVER['HTTP_USER_AGENT']);

if ($ua->mobile) {
    $APP->template->file('mobile/index.html')->display($content);
} else {
    $APP->template->file('desktop/index.html')->display($content);
}
```

### Конфигурация из произвольного файла

```php
// Прочитать любой INI-файл
$settings = $APP->config->readFile('app/settings.ini');

// Прочитать конфиг текущего фасада (внутри файла фасада)
$config = $this->config->get(__file__);

// Сохранить конфиг
$APP->config->set($newConfig, 'engine/facades/myservice.ini');
```

## Преимущества и недостатки подхода

### Преимущества

**Простота использования**
Не нужно думать о создании объектов и передаче зависимостей.
`$APP->template` всегда готов к работе.

**Ленивая загрузка**
Фасад инициализируется только при первом обращении.
Неиспользуемые сервисы не потребляют ресурсы.

**Лёгкое расширение**
Добавить новый сервис = создать один PHP-файл.
Никакой регистрации в контейнере, никаких конфигов маппинга.

**Конфигурация рядом с кодом**
Каждый фасад хранит свой `.ini` файл в той же директории.
Легко найти и изменить настройки конкретного сервиса.

**Зависимости между фасадами**
Фасады могут использовать друг друга через `$this` (= `$APP`),
и зависимости разрешаются автоматически при первом обращении.

> [!TIP]
> В случае колец зависимостей фасадов (A->B->C->A), фреймворк самостоятельно их удовлетворит и построит рабочее окружение приложения. Не заботьтесь о петлях. Сосредоточьтесь на разработке.

**Глобальное состояние**
`$APP` — это фактически глобальный объект, создаваемый фреймворком автоматически, удовлетворяя все зависимости и namespace. 
Формально, вы можете создавать свои экземпляры APP (включая форки $myAPP = clone $APP), но в реальной разработке пока не выявлены паттерны, при которых это было бы необходимо. 


### Недостатки

**Неявные зависимости**
Из сигнатуры функции не видно, какие фасады она использует.
Зависимости скрыты внутри тела функции.

**Отсутствие строгой типизации**
`$APP->template` возвращает `mixed` с точки зрения IDE.
Автодополнение работает хуже, чем при явном DI.

**Более сложное наследование**
Наследование интерфейса (фасада), хоть и не является сложной задачей, но требует начально понимания АОП (агентно-ориентированного программирования), что может вызывать сложности программистов, работающих только в паттернах ООП.

## Сравнение с Dependency Injection

| Критерий | Фасады Quark | DI-контейнер |
|----------|-------------|--------------|
| Простота добавления сервиса | Создать файл | Создать класс + зарегистрировать |
| Явность зависимостей | Неявные | Явные (в конструкторе) |
| Тестируемость | Сложнее | Проще (моки через конструктор) |
| Производительность | Ленивая загрузка | Зависит от реализации |
| Порог входа | Низкий | Выше |
| Подходит для | Небольших и средних проектов | Крупных enterprise-проектов |

Фасады Quark — это осознанный выбор в пользу простоты и скорости разработки. 
Для большинства веб-приложений это оптимальный баланс между удобством и архитектурной чистотой. Основная миссия применения теории интерфейсов в Quark - как можно меньше беспокоить разработчика формальным исполнением соглашений. Максимально убирая "бюрократический" код, разработчики фреймворка преследуют цель создать среду, которая сама подталкивает к простым и изящным решениям, а не накладывает обременяющие и формализующие ограничения.

Убирая все лишнее, реализуется парадигма: **Крайне сложно ошибиться в коде, который не нужно писать.**
Удачного пользования продуктом!
